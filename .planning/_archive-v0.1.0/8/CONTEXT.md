# Phase 8: Retention And Lifecycle - Context

Gathered: 2026-08-22
Feeds: /cad-plan 8

## Scope boundary

In: retention policy (off by default, keep/evict/delete, global or per project) running as a bounded step inside the ingest pass, with a `--dry-run` report; capture modes `full`/`lean`/`minimal` eliding at the blob; `verbatim compact`, `verbatim usage`, `verbatim export`, `verbatim data move`; rolling snapshots on by default. Requirements RET-01..RET-05, ING-07, STOR-06, STOR-07, PRIV-04.
Out: multi-machine sync and encryption at rest (project Out of Scope); ingest-time REDACTION, which stays out of scope and is a different thing from capture-mode elision - elision drops a whole named subtree and marks that it did, it never rewrites content in place; a `repair` command or external supervisor; changing what `verbatim verify` reports about a genuinely corrupt blob.
Deferred: network-filesystem DETECTION for `verbatim data move` - the command warns and confirms instead of refusing, because no `std` API detects a network mount on any of the three targets and the alternative is a new platform-specific dependency on the hook-path binary (D-16). A tombstone table for `delete` - the transcript-gone rule (D-02) removes the need unless deletion at an age below Claude Code's own `cleanupPeriodDays` default of 30 turns out to be wanted.
Plan shape: multiple plans, same phase. The seams: retention proper (AC1-AC3), lifecycle ops (AC4-AC6), capture mode (AC7).

## Durable decisions

- D-01 (Retention config): Retention is configured only by hand-edited `verbatim.toml` - a new `[retention]` table on `FileConfig` - and per-project keys are matched through the SAME normalizer `exclude` already uses, not by string equality against `session_meta.project`. No command ever writes the file. Evidence: `crates/verbatim-core/src/config.rs:85-101` (`FileConfig`, `#[serde(default)]` per table, unknown keys ignored), `config.rs:348-357` (`from_parts` normalizes exclusions into path strings), `config.rs` `Config::excludes_path` component rule, root `Cargo.toml` (`toml` is `default-features = false, features = ["std","parse","serde"]` - the serializer half is deliberately absent and nothing in either crate calls `toml::to_string`), `DESIGN-BRIEF.md:361-378`. If wrong: the brief's own example `[retention.project.scratch]` is a bare short name while every stored project key is a canonical git toplevel like `/data/code/scratch`, so a string-equality match silently matches nothing and retention reports "0 sessions" forever, reading as broken rather than misconfigured; keying on bare basenames instead makes two same-named projects share one policy and one of them deletes the other's data.

- D-02 (Retention/delete): `delete` acts ONLY on sessions whose transcript no longer exists on disk - it is a garbage collector for what Claude Code's own `cleanupPeriodDays` already removed, not an independent age rule. Evidence: `crates/verbatim-core/src/recover.rs:132-148` - the orphan sweep deletes every `watermarks` row with `byte_offset <> 0` where `NOT EXISTS (SELECT 1 FROM sessions ...)`, and `recover::recover` runs at the top of EVERY pass and every single-file ingest before any transcript is read; `crates/verbatim-core/src/discover.rs` yields transcripts by filename alone with no store consultation; `crates/verbatim/src/cmd/doctor.rs` checks `cleanupPeriodDays`, whose default is 30 (`DESIGN-BRIEF.md:102`). If wrong: a deleted session's file is rediscovered on the next hook spawn and re-ingested from offset 0, so `verbatim compact` reclaims nothing measurable and AC4 fails intermittently depending on whether a hook fired between the delete pass and the compact.

- D-03 (Retention/evict): `evict` keeps the `sessions` row with an emptied blob and sets `session_meta.is_evicted`, and `verify`, `reindex` and the ingest append path EACH need an explicit `is_evicted` arm - none has one today. Evidence: `crates/verbatim-core/src/store/schema.rs` declares `blob BLOB NOT NULL`, so the row cannot carry a null; `crates/verbatim-core/src/verify.rs:93-110` selects `s.blob` for every row and calls `blob::read_all`, which fails on an empty blob and would report every evicted session as corrupt - exactly the confusion phase 3 D-08 exists to prevent; `crates/verbatim-core/src/reindex.rs:78-120` rebuilds `turns`/`turns_fts` from `sessions.blob` alone and pushes an unreadable blob onto `Rebuilt::failed`; `crates/verbatim-core/src/ingest/mod.rs` `Existing::read` + `prefix_matches` call `blob::read_all(&session.blob)` on the resume path. If wrong: AC2 passes on the day retention runs and fails on the next `DERIVED_SCHEMA` bump, because `recover::recover` calls `reindex::open_up_to_date` at the top of every run - the evicted sessions lose their turn and FTS rows inside the ingest lock with only a `Rebuilt::failed` note to show for it, which is silent data loss reporting as retention working correctly.

- D-04 (Retention/dry-run): RET-03's `--dry-run` is `verbatim retention --dry-run`, its own `--json` data command, and it shares ONE evaluation function with the pass-embedded retention step. Retention still RUNS in the pass per RET-03; this command only reports. Evidence: `crates/verbatim/src/cmd/ingest.rs:78-96` (`parse` accepts a single positional and rejects every flag); `crates/verbatim/src/main.rs:93-145` (`ingest` is not a `--json` data command and prints only to stderr, so a dry-run report there has no documented shape); no `dry_run`/`dry-run` string exists anywhere in `crates/` or `docs/`. If wrong: two independently written evaluations of a `'now'`-relative SQL predicate run at two different wall-clock instants and can legitimately disagree by one session, which makes AC3's "the subsequent real pass acts on exactly that set" unfalsifiable rather than false.

- D-05 (Capture mode): Elision happens at ingest on the record's JSON line BEFORE it enters the blob, targeting the top-level `toolUseResult` and `attachment` objects and replacing each with a marker key so the line stays valid JSON. Only `full` keeps the blob byte-identical to the transcript. Evidence: `crates/verbatim-core/src/index/text.rs:16-23` names the top-level `toolUseResult` ("41% of the corpus by bytes") and the top-level `attachment` object as identifiable without parsing a message body; `crates/verbatim-core/src/parse/record.rs` classifies purely off top-level fields; `crates/verbatim-core/src/reindex.rs:98-120` re-parses the STORED stream and re-derives everything from it; `crates/verbatim-core/src/verify.rs` checksums what is stored, not the file (phase 1 D-06) - so an elided-but-well-formed stream survives `verify`, `reindex`, `recall_get` byte ranges and `turns.stream_offset`/`byte_len` unchanged; `crates/verbatim-core/tests/ingest.rs:89` `the_blob_reproduces_the_transcript_byte_for_byte` is the test AC7 keeps for `full` only. Measured 2026-08-22 on the live store: the archive table is 469,413,888 of 1,103,396,864 bytes (42.5%). This NARROWS phase 1 D-13 and phase 2's byte-for-byte invariant to the `full` mode rather than overturning them, which is why ROADMAP moved AC7 out of phase 2 and into this phase. If wrong: eliding anywhere later (derived tables only) leaves the archive at full size, so "progressively fewer bytes" becomes an index-only claim capped at the ~32% `turns_fts_data` occupies and the brief's ~50% / ~10-15% figures are unreachable.

- D-06 (Store location): The location pointer is a new plain-text file in verbatim's config directory, read by `data_dir()` BELOW `VERBATIM_DATA_DIR`, and `verbatim data move` relocates the WHOLE data directory, not just `verbatim.db`. Evidence: `crates/verbatim-core/src/config.rs:759-765` (`config_dir()`, the mirror-image resolver) and `DESIGN-BRIEF.md:405`; the `toml` dependency is parse-only with no serializer, so a TOML pointer would cost a new cargo feature on the hook path; the directory holds more than the database - `LOCK` (`crates/verbatim-core/src/ingest/lock.rs:27`), the per-session injection state directory (`crates/verbatim-core/src/ingest/pass.rs:159`, `inject::decision::DIR_NAME`, phase 5 D-06), and `verbatim.db-wal`/`-shm` (`crates/verbatim/src/cmd/status.rs:168-180` sums all three for `size_bytes`). If wrong: a move that copies only `verbatim.db` strands the undrained decision files, and the next pass's `feedback::drain` reports "the decision log could not be drained" into `runs.error` while FEED-03's replay history is silently left behind at the old path. A pointer read added to `data_dir()` also lands on the hook path, whose p99 budget is asserted at 10 ms with a measured 0.408 ms floor (`crates/verbatim/tests/hook.rs:343-376`) - the read must be cheap or conditional.

- D-07 (Snapshots): Snapshots use `VACUUM INTO`, not rusqlite's online backup API. Evidence: root `Cargo.toml` pins `rusqlite = { version = "0.40", features = ["bundled"] }`; rusqlite 0.40.2's own `Cargo.toml:75` declares `backup = []` and `src/lib.rs:118-119` gates `pub mod backup;` behind it. Measured 2026-08-22 against the live 1,103,396,864-byte store: `VACUUM INTO` completed in 0.56 s producing a 1,086,840,832-byte file that opens with all 3,416 sessions, `journal_mode=delete`, `PRAGMA integrity_check` = ok; on a synthetic WAL store it succeeds while a second connection holds an open `BEGIN IMMEDIATE` and excludes that transaction's uncommitted row, where plain `VACUUM` fails with `database is locked`. If wrong: a plan reaching for `rusqlite::backup::Backup` does not compile, and enabling the feature is an unbudgeted change to the hook-path binary that every other dependency in the root `Cargo.toml` carries a justification comment for.

- D-08 (Compaction): `verbatim compact` is `VACUUM` followed by `PRAGMA wal_checkpoint(TRUNCATE)`, taking the ingest lock the way `uninstall --purge` does. Evidence: measured 2026-08-22 on a synthetic WAL store, per file - after inserts db 15,065,088 / wal 0; after deleting half and checkpointing, db 15,065,088 / wal 0 with `freelist_count` 1,800; after `VACUUM`, db 7,540,736 / **wal 7,584,952**, a TOTAL up from 15.06 MB to 15.13 MB; after `wal_checkpoint(TRUNCATE)`, db 7,540,736 / wal 0. `crates/verbatim/src/cmd/status.rs:168-180` sums `verbatim.db`, `-wal` and `-shm` for both the human line and `--json`'s `size_bytes`; plain `VACUUM` fails outright while another connection holds a write transaction (`crates/verbatim-core/src/ingest/lock.rs`, `crates/verbatim/src/cmd/uninstall.rs:438`). If wrong: AC4's "reduces the on-disk store size" fails as written - the size the product itself reports goes UP immediately after `compact`, and the failure is timing-dependent on whether anything checkpointed in between.

- D-09 (Usage): `verbatim usage` reports TWO independent tables - archive bytes by project and by month, and store footprint by table - and the archive totals reconcile to `sum(length(sessions.blob))`, never to the on-disk file size. Evidence: measured 2026-08-22 via `dbstat` on the live store, total file 1,103,396,864 bytes: `sessions` 469,413,888 (42.5%), `turns_fts_data` 350,846,976, `turns` 103,686,144, `sqlite_autoindex_turns_1` 56,299,520, `idx_turns_uuid` 23,121,920, `entities` 18,620,416, `idx_entities_lookup` 18,186,240, `idx_turns_ts` 17,891,328, `paths` 10,940,416, `idx_paths_path` 10,887,168; `SELECT sum(length(blob)) FROM sessions` is 465,985,120, 42.2% of the file. `crates/verbatim/src/cmd/status.rs:168-180` already owns the on-disk figure. AC4 below carries the corrected wording. If wrong: per-project totals are asserted against a number 2.4x larger than everything the projects account for, and the test either fails or is written to a tolerance so wide it proves nothing; attributing derived bytes pro-rata instead would make every per-project number an estimate, so a user comparing two projects compares a model rather than a measurement.

## Decisions

- D-10 (Retention placement): Retention is a new step inside `pass::locked`, after `observe::observe_new` and before `record_pass`, bounded by a `MAX_PER_PASS`-style constant, reporting through a `Summary` field whose `lines()` fold into `runs.error`. Evidence: `crates/verbatim-core/src/ingest/pass.rs:129-223` is the whole lock scope and `:186-204` the existing end-of-pass order (drain, walk, `outcomes`, `observe_new`, `record_pass`); `crates/verbatim-core/src/observe/mod.rs:66-75` declares `pub const MAX_PER_PASS: usize = 100` with exactly this reasoning and is the only precedent for RET-03's "bounded work per pass". If wrong: retention placed after `record_pass` cannot report into `runs.error`, and with no log file by design there is nowhere for a pass that evicted nothing to say why.

- D-11 (Retention age): A session's age is `session_meta.last_turn_at` compared lexicographically in SQL against `strftime('%Y-%m-%dT%H:%M:%fZ','now','-N days')`, and retention only considers sessions the idle rule has already closed (`is_final = 1`). Evidence: `crates/verbatim-core/src/feedback/finalize.rs:47-58` is exactly this statement shape and states why (fixed-width ISO-8601 UTC text, so string order is time order and no date parsing happens); `crates/verbatim/src/cmd/mod.rs:135-164` (`time_bound`) applies the same rule at the CLI; `crates/verbatim-core/src/ingest/pass.rs:191-203` sets `is_final` earlier in the same pass, so a session can be finalized and aged out on one pass. If wrong: keying on `first_turn_at` ages out a long-running session still being appended to, and skipping the `is_final` gate evicts a live transcript's blob - after which the next pass's `blob::append` fails its checksum precondition and the file is recorded as a per-file failure on every pass thereafter.

- D-12 (Capture mode): "Tool result" is NOT identifiable from the derived tables and must be recognized from the record JSON. Evidence: measured 2026-08-22 against the live store (3,416 sessions / 432,242 turns / 1,556,598,685 uncompressed stream bytes), `SELECT count(*) FROM turns WHERE record_type='user' AND tool_name IS NOT NULL` returns 0, while the same query for `assistant` returns 104,794 - and `user` records hold 891,419,639 bytes, 57.3% of the stream (assistant 31.1%, attachment 8.7%, system 0.5%). If wrong: a `lean` implementation filtering on `turns.tool_name` elides nothing at all and the mode ships storing the same bytes as `full`.

- D-13 (Capture mode): The mode a session was captured under is recorded in a new `session_meta.capture_mode` column, appended at the END of the table in both `CREATE_SQL` and `BRING_FORWARD_COLUMNS` (D-19). Evidence: `crates/verbatim-core/src/store/schema.rs` has no such column and `crates/verbatim-core/src/store/open.rs:36-46` defines only `META_ARCHIVE_FORMAT` and `META_DERIVED_SCHEMA`, so nothing records it today; `crates/verbatim-core/src/blob/writer.rs` `append` copies completed blocks across untouched and recompresses only the trailing partial block, so bytes written under an earlier mode are never revisited and a store whose mode changes mid-life holds a mix inside one blob. Per-session rather than a store-wide `meta` key because AC7's byte-for-byte claim for `full` has to be assertable about a session in an existing store, not only about a store built from scratch. If wrong: `verify` and `reindex` stay correct either way (both read stored bytes), but nothing can answer "was this session captured lean".

- D-14 (Store location): The store path has exactly ONE resolver, and neither the hook argv nor the MCP registration names it - so STOR-07 is a change to `store::data_dir()` alone and AC5's "no settings.json change" is already structurally true. Evidence: `crates/verbatim-core/src/store/open.rs:595-599` is the only resolver (`VERBATIM_DATA_DIR`, else the platform directory); every other site takes `data_dir: &Path` as a parameter, with two product call sites at `crates/verbatim/src/cmd/mod.rs:85-87` and `crates/verbatim/src/cmd/install/mod.rs:145`; `crates/verbatim/src/cmd/install/targets.rs` writes hook entries as `args: ["hook", <event>]` and the MCP entry as `args: ["mcp"]`, no store path in either; `crates/verbatim/src/cmd/spawn.rs:72-75` inherits the environment unchanged. If wrong: a plan assuming settings.json carries the store path would rewrite the hooks object and break INST-03 and phase 4 AC3.

- D-15 (Snapshots): "Rolling snapshots run by default" is a timestamp row in `meta` gating the snapshot to at most once per 24 hours, pruning to the last 3, running OUTSIDE the ingest lock the way phase 7's `judge_new` does (`crates/verbatim-core/src/ingest/pass.rs:115-126`); both the interval and the retained count are `verbatim.toml` keys. Evidence: `DESIGN-BRIEF.md:100-101` is the whole specification; nothing in `pass.rs` schedules periodic work and the only cadence mechanism in the product is "the hook spawn is the scheduler" (`crates/verbatim-core/src/ingest/lock.rs:1-19`), which fires on every prompt; a snapshot of the real store is 1.087 GB and 0.56 s (D-07), so a naive per-pass snapshot writes a gigabyte per prompt. If wrong: snapshots on by default fill the data directory at roughly one archive-size per pass and the first user to notice is one whose disk fills.

- D-16 (Store location): `verbatim data move` WARNS about the SQLite-over-network-filesystem hazard and confirms, rather than refusing network mounts as `DESIGN-BRIEF.md:407` specifies. Evidence: no `std` API detects a network filesystem on any of the three targets (Linux `statfs` `f_type`, macOS `getattrlist`, Windows `GetDriveType`/`WNetGetConnection` are each a platform-specific dependency on the hook-path binary); `data move` is a human-only interactive command (D-17), so it asks regardless of destination and the warning costs nothing. If wrong: a user relocates onto SMB or NFS and SQLite's locking off local disk behaves in ways this repo has not measured - the warning is the mitigation, not the fix. Detection is Deferred above.

- D-17 (CLI surface): `retention`, `compact`, `usage` and `export` join `DATA_COMMANDS` and `docs/json-shapes.md` as `--json` data commands; `data move` is human-only like `install` and `uninstall`, and its two-word form follows the `observations regenerate` nested-dispatch precedent with its own envelope `command` string. Evidence: `crates/verbatim/tests/cli.rs:740-800` - `DATA_COMMANDS` is the swept contract table whose comment says a later-phase data command "joins `DATA_COMMANDS` on one line and is held to the whole contract by that alone"; `docs/json-shapes.md:1-5` states the same; `crates/verbatim/src/main.rs:135-143` explains why `install`/`uninstall` are deliberately NOT data commands ("it shows a diff and asks once, and a single JSON document on stdout cannot be both of those things"), which is `data move`'s shape exactly; `crates/verbatim/src/cmd/observations.rs:39-44, 442-478` is the only two-word dispatch. If wrong: a `data move` written as a data command has to be non-interactive, and an irreversible relocation with no confirmation contradicts the one place this product asks before acting (`crates/verbatim/src/cmd/uninstall.rs:455-467`).

- D-18 (Usage): `usage` buckets a session into one month by `substr(first_turn_at, 1, 7)`, and the null-`first_turn_at` and null-`project` rows each get an explicit bucket rather than vanishing. Evidence: measured 2026-08-22 on the live store - 2 distinct `substr(first_turn_at,1,7)` values across 3,416 sessions, 1 session with a null `first_turn_at`, 0 sessions where `substr(first_turn_at,1,7) <> substr(last_turn_at,1,7)`, 60 distinct `project` values with 1 null; `crates/verbatim-core/src/ingest/mod.rs` `write_session_meta` establishes `first_turn_at` by byte order and coalesces it so a tail pass never revises it; `crates/verbatim-core/src/config.rs:1023-1052` (`visible::projects`) is the gate a per-project report must go through, since exclusion is retroactive (ING-08, phase 2 D-23). If wrong: a session written across midnight on the last of a month files all its bytes under the earlier month - zero sessions today - and unbucketed nulls silently break totals that are supposed to reconcile.

- D-19 (Schema): Any new retention table reaches an already-initialized store through `bring_forward`'s missing-table arm with NO `DERIVED_SCHEMA` bump, and any new column is appended at the END of its table in both `CREATE_SQL` and `BRING_FORWARD_COLUMNS`. Evidence: `crates/verbatim-core/src/store/open.rs:118-131` and `bring_forward` at `:330-378` - the missing-table arm re-runs `CREATE_SQL` (every statement `IF NOT EXISTS`) inside one transaction; `crates/verbatim-core/src/store/schema.rs`'s `TABLES` comment records phase 6 D-02 and phase 7 D-01 landing `decisions`, `labels` and `observations` on exactly those terms, and `BRING_FORWARD_COLUMNS`'s doc block states the append-at-the-end ordering rule explicitly. Phase 5 D-14 is SUPERSEDED; the code reflects the phase 6/7 mechanism. Live confirmation this path is not hypothetical: the store at `~/.local/share/verbatim/verbatim.db` (1.10 GB, 304 `runs` rows, last run 2026-08-22T22:33:40Z) carries none of `decisions`, `labels`, `observations`, because the installed binary predates them - a phase 8 binary brings forward three tables plus whatever retention adds on the first hook-spawned pass. If wrong: a column inserted mid-table gives a fresh store and an upgraded store different column orders, and any `SELECT *` or positional `r.get(n)` diverges between the two; a tombstone or retention table left out of `schema::TABLES` never reaches the store that has actual data.

## Acceptance criteria

- [ ] AC1: With no `[retention]` block in verbatim.toml, an ingest pass over a corpus whose newest session predates any default deletes zero sessions and evicts zero, and `verbatim sessions` returns the same count before and after.
- [ ] AC2: After a pass evicts a session, `verbatim sessions` still lists it, a search that matched one of its turns still returns that turn, and `recall_get` on that turn returns `body_evicted` - and all three still hold after `verbatim reindex`. A deleted session appears in neither the listing nor the search.
- [ ] AC3: `verbatim retention --dry-run --json` names the session ids it would evict and delete and leaves every table row unchanged; the subsequent ingest pass acts on exactly that set of ids.
- [ ] AC4: After a delete pass, `verbatim compact` leaves `verbatim status`'s reported `size_bytes` (db + wal + shm) strictly smaller than before it ran, and `verbatim usage --json` reports archive bytes per project and per month summing to `sum(length(sessions.blob))`, plus a store-footprint table whose rows sum to the database file size.
- [ ] AC5: `verbatim data move <path>` relocates the database, LOCK and injection-state directory to a new path, after which a hook invocation and an MCP `recall_search` both read the new location with settings.json byte-identical to before the move.
- [ ] AC6: A snapshot taken while an ingest pass holds the lock opens as a store, passes `verbatim verify` with no findings, and contains every session committed before that pass started.
- [ ] AC7: Ingesting one transcript under `full`, `lean` and `minimal` stores strictly decreasing blob bytes; every elided record under `lean` and `minimal` carries the elision mark; the `full` store reproduces the transcript byte for byte.

## Flagged assumptions

- Claude Code writes transcripts append-only and never truncates or rewrites one in place - user observation, unconfirmed with Anthropic and carried forward unresolved from phase 2 (`.planning/phases/2/CONTEXT.md:57`); if wrong: D-02's transcript-gone delete rule stays SAFE (a truncated file simply means the session is not deleted), but D-05's elision and the divergence flag interact in ways only Anthropic can settle.
- SQLite's `VACUUM` and its locking behaviour on the filesystems `data move` may land on - SMB/NFS destinations, and Windows `\\?\`-prefixed long paths - are unmeasured by this repo; if wrong: `verbatim compact` on a relocated store fails or corrupts in a way D-16's warning only mitigates.
- Network-filesystem detection for `data move` is deferred, so `DESIGN-BRIEF.md:407`'s "refuse network mounts by default" is not met this phase; if wrong: a user relocates onto a network mount that a refusal would have caught.
- The `lean`/`minimal` byte savings reach the brief's ~50% / ~10-15% figures - Likely, from the measured distribution (D-12: user records 57.3% of the stream, records over 8 KB 52.0%) but not from an implemented elision; if wrong: AC7's "strictly decreasing" still holds while the modes are not worth choosing.
- Phase 2's open item that the crash harness's `Snapshot` excludes `compaction_boundaries` (`.planning/phases/2/SUMMARY.md`) - if AC6's snapshot test reuses that harness, the comparison is incomplete on that one table.
