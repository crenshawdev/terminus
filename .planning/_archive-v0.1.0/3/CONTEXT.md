# Phase 3: Recall - Context

Gathered: 2026-08-12
Feeds: /cad-plan 3

## Scope boundary

In: Rust-side text expansion into `turns_fts` (RCL-01), entity extraction of the five kinds from structured tool records with per-kind normalization (RCL-02, RCL-03), the per-turn entity cap and query-time IDF weighting (RCL-04), the `search` / `show` / `sessions` terminal commands with project scoping and filters (RCL-05), the `--json` contract and exit codes across every data command including the three phase 1/2 commands (RCL-06), and `verbatim mcp` - a short-lived stdio JSON-RPC server exposing `recall_search`, `recall_context` and `recall_get` (RCL-07 .. RCL-11). Also the read-path half of exclusion that phase 2 D-23 left to this phase, and the `DERIVED_SCHEMA` bump plus rebuild that a change to `turns_fts` body shape forces.
Out: Hooks, install, MCP registration in settings.json and bounded-parallelism backfill (phase 4). The SessionStart resume brief, prompt-time injection and the derivation of a dropped-turn set from `compactMetadata` (phase 5, INJ-05). Decision logging, outcome labels and replay (phase 6). Retention, eviction and deletion - `session_meta.is_evicted` stays null and is written only by a fixture here (phase 8). Enabling rusqlite's `blob` feature for incremental blob I/O.
Deferred: None.
Plan shape: multiple plans, same phase. Natural seams: derivation (AC1-AC3), terminal recall and the JSON contract (AC4-AC5), the MCP server (AC6-AC7), with the third depending on the second's query layer.

## Durable decisions

- D-01 (Index derivation): `turns_fts.body` is a per-record-type text projection - message text blocks, tool inputs, tool-result stdout/stderr - plus the expansion tokens, never the raw JSON line. Evidence: `crates/verbatim-core/src/derive.rs:96-99` indexes `String::from_utf8_lossy(row.record)`, the whole line; measured on sqlite 3.53.4 against a table declared as `crates/verbatim-core/src/store/schema.rs:150-151`, a row holding one raw transcript line is returned by `MATCH 'assistant'` because `"type":"assistant"` is indexed as text. Byte shares in a 180-file / 26,865-record sample: `user` 57.9%, `assistant` 30.5%, `attachment` 8.5%, so tool-result payloads dominate whatever is indexed; 0 `image` content blocks, so base64 is not the driver. The blob keeps the verbatim copy, so D-13 (phase 1) is intact and a projection change stays replayable for FEED-03. If wrong: free-text search returns most of the archive for any word that is also a JSON key or record type (`assistant`, `content`, `text`, `type`), and BM25 ranks turns by scaffolding frequency, so phase 5's rank-1..3 structural threshold fires on noise.
- D-02 (Index derivation): Entities are extracted from the same record's own bytes - `message.content[]` `tool_use` / `tool_result` blocks plus the top-level `toolUseResult` object - with no cross-record join between a call and its result. Evidence: 180-file sample carries 5,208 `tool_use` and 5,208 `tool_result` blocks with `toolUseResult` present as a dict on 4,858 records; per-tool input keys measured `Bash.command` 3,014, `Read.file_path` 945, `Edit.file_path`/`old_string`/`new_string` 573 each, `Write.file_path` 115, `Grep.pattern` 93, `Grep.path` 61; `toolUseResult` keys `stdout`/`stderr`/`interrupted` 2,920, `filePath` 679, `structuredPatch` 677. `crates/verbatim-core/src/parse/record.rs:298-313` already walks `message.content` for `tool_name` and names RCL-02 as the extension point. If wrong: joining `tool_use` to its `tool_result` across records needs a `tool_use_id` index and a second pass, which breaks the one-record-in / one-row-out shape of `derive_turn` and with it the single ingest/rebuild seam at `derive.rs:1-20`.
- D-03 (Index derivation): The error signal is `tool_result.is_error == true` plus a non-empty `toolUseResult.stderr`. There is no exit-code field in the transcript, so RCL-03's "non-zero exits" is read off those two. Evidence: 180-file sample has `is_error: true` on 151 of 5,208 `tool_result` blocks; a 300-file sample has 4,995 `toolUseResult` objects carrying a `stderr` key, 179 non-empty, and 250 `is_error` blocks. A key scan for `/exit|code|status|success/i` across every `toolUseResult` in that sample found only `status` (122), `returnCodeInterpretation` (65), `success` (31) and `code` (25), all on non-Bash tools; Bash results carry `stdout`, `stderr`, `interrupted`, `isImage`, `noOutputExpected` and nothing else. `DESIGN-BRIEF.md:211` states the source as "non-zero exits, stderr, panics" and is the claim this measurement corrects. If wrong: the extractor looks for an exit code that does not exist, emits zero `error` entities across the whole corpus, and the highest-precision signal in phase 5's hierarchy (`DESIGN-BRIEF.md:249`) is permanently empty while every synthetic-fixture test still passes.
- D-04 (Index derivation): RCL-03 normalization strips UUIDs, timestamps, `0x` addresses and `:line:col` suffixes, and deliberately stops short of stripping bare integers. Evidence: 400-file sample, 1,117 error lines, 440 carrying a variable part, 367 distinct raw values of which 44 recur across two or more sessions. Under UUID/timestamp/address/line-col normalization: 350 distinct, 46 recurring. Adding bare-integer stripping: 338 distinct but only 39 recurring - over-stripping merges genuinely different errors, so the aggressive rule scores worse on the property the rule exists for. If wrong: an aggressive rule ships and two unrelated failures share one entity value, which is a phase 5 false-positive injection the feedback loop will label but not explain.
- D-05 (Read path): Excerpts are cut from the session blob, not from FTS5. Evidence: measured on sqlite 3.53.4 against `fts5(body, content='', contentless_delete=1)` as declared at `crates/verbatim-core/src/store/schema.rs:150-151`, `snippet(f,0,'[',']','...',8)` returns an empty string with exit 0 while `bm25(f)` still ranks (`-1.0e-06`); the blob read path is `crates/verbatim-core/src/blob/reader.rs:65-105` with the working pattern at `crates/verbatim-core/src/testkit.rs:285-310`. If wrong: every hit in `verbatim search --json` and `recall_search` carries an empty `excerpt` that validates against the documented shape and tells the model nothing, so the defect shows only on inspection of values, never on a schema test.
- D-06 (Read path): A `recall_context` window stops at the session boundary; it does not follow `continues_from` or `parent_session_key`. Evidence: `crates/verbatim-core/src/lineage.rs:1-36` - continuation is a fan-out with zero, one or many successors per link (phase 2 D-02), and 2 of 173 files name a predecessor never ingested (phase 2 D-19); `session_meta.parent_session_key` (`crates/verbatim-core/src/store/schema.rs:81`) is a separate namespace. The response returns the boundary explicitly so a caller can issue a second call. If wrong: `before: 5` on the first turn of a resumed session returns nothing where the previous file holds the answer, or a naive lineage walk crosses into a sibling fork and returns turns from a conversation that never happened.
- D-07 (Read path): Sidechain (subagent) turns are searchable by default and sort below top-level turns at equal score, distinguished by `session_meta.parent_session_key` being non-null. Evidence: phase 2 D-03 put the sidecar's parent in that column specifically so phase 3 could filter subagent turns; measured 7,805 of 19,809 sampled turns (39.4%) carry `isSidechain: true`; `DESIGN-BRIEF.md:239` bars subagent turns from the SessionStart brief and says nothing about search. If wrong: excluded by default, a user who ran a long research subagent cannot find its work and the archive appears to have lost 40% of the turns it holds; ranked equally, two of every five hits come from an agent the user never watched.
- D-08 (Read path): `body_evicted` reads `session_meta.is_evicted`, never a failed blob read. Evidence: `crates/verbatim-core/src/store/schema.rs:79-80` declares `is_final` and `is_evicted`; `crates/verbatim-core/src/ingest/mod.rs:806` states both stay null until retention lands in phase 8, so AC6's fixture sets the column directly. If wrong: a corrupt blob - the thing `verbatim verify` exists to report (`crates/verbatim-core/src/verify.rs:79`) - becomes indistinguishable from a deliberately evicted body, and silent data loss reports as retention working correctly.
- D-09 (CLI contract): The user's query string is tokenized and rebuilt in Rust before it reaches `MATCH`; a raw query is never passed through to FTS5. Evidence: measured on sqlite 3.53.4, `MATCH 'src/worker/S.ts'` fails with `fts5: syntax error near "/"` and exit 1, `MATCH 'foo AND (bar'` and `MATCH '"unbalanced'` likewise - none of these returns an empty result. `REQUIREMENTS.md:43` forbids a non-zero exit for an empty result and searching for a path is the phase's own headline case (`ROADMAP.md:49`). If wrong: `verbatim search src/worker/S.ts`, the most natural command in the product, exits 1 with a SQLite parser message - both the failure RCL-06 names and a failure of success criterion 1's own example string.
- D-10 (CLI contract): `search`, `show`, `sessions` and `mcp` open the store through a read-only path (`SQLITE_OPEN_READ_ONLY`, no `create_dir_all`, no `bring_forward`, no pragma write) and report a missing store as an empty result with a reason. Evidence: `crates/verbatim-core/src/store/open.rs:82-119` currently does `create_dir_all`, then `initialize()` on a fresh path, then `bring_forward` (which issues `CREATE TABLE` / `ALTER TABLE`) and `pragma_update(journal_mode=wal)`, and `crates/verbatim/src/cmd/status.rs:38` already inherits that; RCL-10 requires an empty result with a reason rather than a throw, and a server advertising `readOnlyHint` (ROADMAP success criterion 6) cannot perform DDL on connect. If wrong: `verbatim search` creates a store as a side effect of a read, the MCP server writes schema while claiming to be read-only, and a store on read-only media fails to open at all instead of returning an empty result.
- D-11 (MCP server): The server is a hand-written JSON-RPC 2.0 loop over stdin/stdout using `serde_json`, not the official Rust MCP SDK, and links no async runtime. Evidence: `.planning/PROJECT.md:73` bars an async runtime outright ("cold start is the metric; the hook path must not pay for a runtime it doesn't use"); `crates/verbatim-core/src/lib.rs:1-7` repeats it; `Cargo.toml` has no MCP, tokio or HTTP dependency and every dependency present carries a comment justifying its startup cost; no MCP scaffolding exists anywhere in `crates/`. If wrong: the SDK drags a tokio runtime into the one binary that also serves the hook path, and the startup benchmark `DESIGN-BRIEF.md:498` calls "the product" regresses for every hook invocation, not only for MCP.
- D-12 (MCP server): Current-project auto-scoping is a longest-prefix match of the server's process `cwd` against the distinct `project` and `project_pre_worktree` values already in `session_meta` - no `git` subprocess on the cold-start path. Evidence: `crates/verbatim-core/src/project.rs:100-160` is the only rule that produces a `session_meta.project` key and shells out to git for any `cwd` whose directory still exists, with a 2 s budget (`project.rs:51`); `DESIGN-BRIEF.md:524` records process spawn at 10-30 ms as "the real budget"; `session_meta` carries both keys (`crates/verbatim-core/src/store/schema.rs:82-84`) and matching must consider both (`crates/verbatim-core/src/config.rs:576-581`). Matching against stored keys cannot disagree with what ingest wrote, which resolving independently can. If wrong: either the server pays a git spawn on every cold start for a key it could look up, or it derives the project by a different rule than ingest did and `recall_search` scoped to the current project returns zero hits inside a worktree - the identity fragmentation `PROJECT.md:93` names claude-mem for.

## Decisions

- D-13 (Index derivation): camelCase splitting is the only expansion that changes recall; snake, kebab and path components already tokenize under `unicode61`'s default separators, so RCL-01 emits them for rule completeness rather than for reach. Evidence: measured on sqlite 3.53.4 (the bundled build is 3.53.2, `libsqlite3-sys-0.38.1/sqlite3/sqlite3.h`) over a table declared exactly as `crates/verbatim-core/src/store/schema.rs:150-151` - `MATCH 'manager'` returns the `search_manager_new` row and not the `SearchManager` row, `MATCH 'worker'` returns `src/worker/S.ts`, `MATCH 'sources'` returns `--setting-sources`. If wrong: half of ROADMAP success criterion 1 passes with no expansion written at all, so a phase shipping only path expansion looks 50% correct on the AC and is 0% useful.
- D-14 (Index derivation): Expansion costs the measured 1.16x-1.37x on FTS body bytes, inside the brief's 1.3-1.6x budget, so no index-size mitigation is designed in. Evidence: 80-file sample, 9,499 turns, 37,408,178 turn bytes - full camel+snake+kebab+path expansion of per-turn-unique tokens adds 37.2% (215 tokens/turn), camel-only adds 15.7% (132 tokens/turn), against `DESIGN-BRIEF.md:199`. If wrong: nothing in the phase; both candidate rule sets land inside the budget.
- D-15 (Index derivation): The per-turn entity cap is set in the tens; it binds the tail, not the common turn. Evidence: 300-file sample, 15,449 turns emitting at least one entity under a candidate rule (tool, paths in Bash argv, `file_path`/`path` inputs, paths in Write content and tool-result text) - p50 3, p90 10, p99 38, max 146. `DESIGN-BRIEF.md:218` requires a cap; `REQUIREMENTS.md:41` forbids rejection at index time. Whether the cap is per turn, per kind, or by emitted bytes is the planner's call. If wrong: a cap at 10 silently drops entities from the 10% of turns carrying the most structure - the large tool results most worth recalling - and the loss is invisible because nothing records that a turn was truncated.
- D-16 (Index derivation): `turns.tool_name` is a complete tool filter for RCL-07 - every tool-bearing record carries exactly one `tool_use` block. Evidence: 150-file sample, 19,809 turns; grouping records by `tool_use` block count gives `{1: 4967}` and by `tool_result` block count `{1: 4967}`, no record carrying two, so the first-block capture at `crates/verbatim-core/src/parse/record.rs:298-313` is the only block. If wrong: nothing on this corpus; a future multi-tool record shape silently drops the second tool from the filter, which a corpus snapshot test would catch.
- D-17 (Index derivation): Phase 3 bumps `DERIVED_SCHEMA`, so the first `verbatim ingest` after the upgrade rebuilds every archived session from its blobs inside the ingest lock. Evidence: `crates/verbatim-core/src/store/open.rs:16-27` ("bumped whenever anything rebuildable from the blobs changes shape: `turns`, `compaction_boundaries`, `turns_fts`, `entities`, `paths`"), `crates/verbatim-core/src/reindex.rs:52-141`, with the timing harness already written at `crates/verbatim/tests/corpus.rs:259-299`. If wrong: the bump is skipped and stores written by a phase 2 binary keep unexpanded FTS bodies and empty entity tables, so search silently under-returns on every session archived before the upgrade with no version integer that says so.
- D-18 (Index derivation): A read command never triggers that rebuild - `verbatim search` against a store predating the bump queries the old-shape index rather than repairing it, and says so. Evidence: `crates/verbatim-core/src/reindex.rs:143-152` keeps `open_up_to_date` outside `Store::open` deliberately ("opening a store is a read, and a read that silently rewrites four tables is not one"); `crates/verbatim-core/src/store/open.rs:104-117` runs only the additive column bring-forward on a read open. If wrong: a user who upgrades and searches before the next hook-driven ingest gets degraded results with no message and reports it as a search bug rather than a pending rebuild.
- D-19 (Index derivation): A new index added to `CREATE_SQL` in this phase reaches existing stores only because D-17's bump forces a reindex, not because `Store::open` creates it. Evidence: `crates/verbatim-core/src/store/open.rs:202-244` runs `CREATE_SQL` only when a whole table is missing and returns early otherwise, and `BRING_FORWARD_COLUMNS` (`crates/verbatim-core/src/store/schema.rs:246-270`) covers columns, not indexes, while `crates/verbatim-core/src/reindex.rs:68` runs the full batch. `session_meta` has no index on `project` today (`schema.rs:107-114`), which is the index project-scoped search wants. If wrong: an index exists on fresh stores and silently does not on upgraded ones, so search performance differs between two machines running the same binary with nothing reporting why.
- D-20 (Read path): `recall_get` groups requested ids by `session_key` so each blob decompresses once per request. Evidence: rusqlite's incremental blob I/O is behind an opt-in `blob = []` feature (`rusqlite-0.40.1/Cargo.toml`) that `Cargo.toml:16` does not enable, so existing single-turn reads select the whole blob then open a `BlobReader` (`crates/verbatim-core/src/testkit.rs:295-307`, `crates/verbatim-core/src/reindex.rs:85-89`), and phase 1 D-05 records sessions up to 10.1 MB uncompressed. If wrong: `recall_get` on ids spanning N sessions holds N whole blobs to return N records, while the block-count instrument at `crates/verbatim-core/src/blob/reader.rs:44-53` still reports one block decompressed, so phase 1's AC1 stays green as the read allocates megabytes per hit.
- D-21 (Read path): Every read path applies exclusion through `config::visible`, but with a project-only projection rather than a per-query `visible::sessions()` call. Evidence: `crates/verbatim-core/src/config.rs:473-495` requires every future read path to go through the module, and phase 2 D-23 makes the read half this phase's obligation; measured on a synthetic store shaped like the real one (2,000 sessions, 250,000 turns, warm) the query at `config.rs:532-539` costs 6.2-6.8 ms because of the per-session `count(*)` on `turns` plus the watermark lookup, the same join projecting only `project` costs 0.56-0.58 ms, and `SELECT count(project) FROM session_meta` costs 0.11 ms. If wrong: every `recall_search` and every phase 5 SessionStart pays ~7 ms before the FTS query runs, consuming the whole single-digit-millisecond budget at `DESIGN-BRIEF.md:226`, and the cost is attributed to search rather than to the exclusion gate.
- D-22 (Read path): "Chronological" in `recall_context` means `turn_seq` order, never timestamp order. Evidence: phase 1 D-02, restated at `crates/verbatim-core/src/parse/record.rs:31-36` - 31 of 62 sampled real transcripts carry a record whose timestamp goes backwards; `turns` has `UNIQUE (session_key, turn_seq)` (`crates/verbatim-core/src/store/schema.rs:129`), the covering index a context window needs. If wrong: turns returned around a hit are reordered for roughly half of all sessions and the model reads a reply before the prompt it answers.
- D-23 (Read path): `since` / `until` filters compare `turns.ts` as text, lexicographically, with no date parsing on the stored side. Evidence: 180-file sample - all 22,412 turns carry a timestamp of exactly the shape `NNNN-NN-NNTNN:NN:NN.NNNZ`, one format, UTC only; `crates/verbatim-core/src/store/schema.rs:135` already indexes `turns(ts)`. If wrong: nothing on this corpus; a future offset-bearing timestamp sorts wrongly rather than failing, so the corpus parse test is where drift is caught.
- D-24 (CLI contract): `--json` is retrofitted onto the existing `status`, `verify` and `reindex` commands as well as the three new ones. Evidence: `crates/verbatim/src/cmd/mod.rs:1-6` states the flag, stable shapes and the exit-code contract are RCL-06 in phase 3; `crates/verbatim/src/main.rs:83-90` currently rejects `verify --json` with exit 2 ("silently ignoring them is how `verify --json` comes to look supported"); `REQUIREMENTS.md:43` says every data command. If wrong: `verbatim status --json` still exits 2 after the phase that owns the CLI contract ships, and the retrofit lands in phase 4 beside install, where a shape change to `status` output breaks something already scripted.
- D-25 (CLI contract): JSON is emitted with `serde_json` named directly in the `verbatim` binary crate, adding no newly compiled crate; shapes are never hand-formatted. Evidence: `crates/verbatim/Cargo.toml` lists only `verbatim-core` and `lexopt`, while `serde_json` is already a `verbatim-core` dependency and therefore already linked; the precedent for restraint is explicit at `crates/verbatim/src/cmd/status.rs:10-13`, where rusqlite is deliberately not named in the binary crate. If wrong: shapes get written with `format!` and escaping an excerpt containing quotes, backslashes or control bytes produces `--json` output that fails its own shape validation for exactly the turns most worth reading.
- D-26 (MCP server): `verbatim mcp` is a subcommand of the same binary, dispatched from `main.rs` like every other command. Evidence: `DESIGN-BRIEF.md:478` lists it in the CLI table; `REQUIREMENTS.md:53` (INST-02) points both hook entries and the MCP registration at one copied binary; dispatch table at `crates/verbatim/src/main.rs:64-81`. If wrong: install has two artifacts to place and keep in version lockstep, the version-skew failure class `PROJECT.md:103` says the single canonical binary path exists to retire.
- D-27 (MCP server): The process is bounded by its stdin - it reads framed messages until EOF and exits, holding no socket, no listener and no background thread, and takes no ingest lock. Evidence: `REQUIREMENTS.md:48` (RCL-11) and `PROJECT.md:38,40` make no daemon / no port / no long-lived process a design invariant; reads run concurrently with an ingest pass under WAL, which is why `crates/verbatim/src/cmd/status.rs:6-8` takes no lock either. If wrong: a server surviving its client is the orphaned-process failure class (`PROJECT.md:40`, 157 GB of orphans in the incumbent) reintroduced in the phase whose own requirement forbids it.

## Acceptance criteria

- [ ] AC1: A turn containing `SearchManager` is returned by searches for both `SearchManager` and `manager`, a turn containing `src/worker/S.ts` is returned by a search for `worker`, and a search for `toolUseResult` - a JSON key present on 4,858 corpus records - returns zero hits.
- [ ] AC2: Two turns in different sessions whose stderr differs only in line numbers, addresses, timestamps and UUIDs carry one identical `error` entity value, while two turns whose errors differ only in a bare integer that is not a line number carry two different values.
- [ ] AC3: Over the real corpus, entities of all five kinds are emitted; a `Read` tool_use naming a file emits a path entity while an assistant message naming that same path in prose emits none; no turn carries more entities than the cap; and dropping `turns_fts` and the entity tables and running `verbatim reindex` reproduces the same rows.
- [ ] AC4: `verbatim search src/worker/S.ts` exits 0 with hits, a query matching nothing exits 0 with an empty result set, an unknown flag exits 2, and each of `search`, `show`, `sessions`, `status`, `verify` and `reindex` accepts `--json` and emits JSON on stdout validating against the documented shape with every diagnostic on stderr.
- [ ] AC5: `verbatim search` and `recall_search` return only current-project turns by default and cross-project turns when `project: "*"` is passed; with a project excluded neither path returns any of its turns; and a sidechain turn ranks below a top-level turn of equal score.
- [ ] AC6: `recall_context` returns turns in `turn_seq` order around a hit and returns nothing past the session boundary; `recall_get` on an id whose session has `is_evicted` set returns the record with `body_evicted` rather than an error; and a malformed request returns an empty result carrying a reason.
- [ ] AC7: A spawned `verbatim mcp` fed `initialize` and `tools/list` on stdin reports exactly three tools each marked `readOnlyHint`, opens no listening socket under `ss`, and exits 0 after stdin closes; the same binary run against a nonexistent store path returns an empty result with a reason and creates no file.

## Flagged assumptions

- Four MCP ecosystem facts the codebase cannot answer, left for the planner to pin from live MCP documentation before the server task is written - Unclear: where `readOnlyHint` sits on a tool descriptor (under `annotations` or not), which `protocolVersion` string Claude Code's client negotiates today, how Claude Code terminates a stdio MCP server (stdin close vs SIGTERM vs kill) on each platform, and whether the client surfaces a reason string on an empty result versus requiring a JSON-RPC error. If wrong: AC7's `readOnlyHint` assertion tests a field name nothing reads, or RCL-10's empty-result-with-reason contract is invisible to the only client that matters.
- Whether the official `rmcp` Rust SDK has a runtime-free stdio transport - Unclear; nothing in the repo pins its dependency graph. D-11 chose the hand-written loop on the no-async-runtime constraint alone, so if the SDK turns out to be runtime-free the decision was still safe, just possibly more work than needed.
- Whole-blob materialization on the read path - Likely; rusqlite's `blob` feature is not enabled and enabling it is out of scope, so D-20's grouping by `session_key` bounds the cost per request without eliminating it. If wrong in the direction of large sessions dominating recall traffic, `recall_get` allocates megabytes for single records and phase 5's budget absorbs it silently.
- AC2 is proved by a constructed fixture, not by a corpus statistic - Confident. The normalization rule buys 44 recurring error values against 46 on the real corpus (367 distinct raw values), so no corpus-wide collapse ratio can back the criterion; the planner should not write a test asserting one.
- Phase 2 left the continuation rate unreconciled - Confident: CONTEXT measured 180/1,253 files = 14.4% while the SUMMARY reports 188 links = 8.8% of sessions, two different denominators nobody has squared. Worth one look before anything in this phase or phase 5 depends on the rate.
- The `agent-*.meta.json` format stored opaquely by phase 2 D-04 is undocumented and may drift - Likely stable. This is the phase that first tries to extract `description` from it for ranking, so this is where the drift surfaces; nothing at ingest breaks because the bytes are stored unparsed.
- Whether the entity cap binds per turn, per kind, or by emitted bytes is left to the planner - D-15 fixes the magnitude, not the shape.
