Deviations:
- [deviation] Task 1's Verify names `src/worker/S.ts` as "the stored value" whose exact match a new case should report. It is not stored: `session-recall.jsonl` carries that path in PROSE only, and RCL-02 extracts entities from structured tool records and never from a sentence, so no `entities` row for it exists and its hit reports no kind at all. The fixture's only stored path value is `docs/RETRY.md`, from its `Read` tool call, and the new cases use it; `src/worker/S.ts` now serves the same Verify's free-text control ("a hit that matched only as free text reports no kind and 0"), which is what it can actually prove.
- [deviation] The same Verify's covered case - "the same path inside a longer question reports the covered kind" - cannot be observed through a search as written, and the reason turned out to matter for the whole plan. A `Query` is conjunctive (D-09), so `who edited docs/RETRY.md yesterday` returns NO hits against a store whose `Read` opened exactly that file: every word of the prompt has to be in the turn. The covered kind is asserted with `Read docs/RETRY.md` instead, whose extra token the turn itself carries.
- [deviation] Task 4's Action pictures "one project-scoped search" over the prompt's own `Query`, which the finding above makes vacuous: injection built on that expression fires only when a turn repeats the user's sentence, so AC3 would pass for a bare-path fixture prompt and be permanent silence for anything a person types. The threshold, the limit of 10, the cap of 3 and the excerpt deferral are all exactly as the task asks; what changed is the expression that gathers the candidates. `Request::candidates` carries the spellings the prompt NAMES - resolved paths, the relative spelling, and identifier-shaped tokens, capped at 8 - each conjoined within itself and disjoined across, and the prose stays in `Request::query` where it still weighs and excerpts what comes back. Both existing front ends are byte-identical: an empty `candidates` is the expression `search::run` always built, and `verbatim search` and `recall_search` still pass unedited. Untrusted input never reaches `MATCH` as written - every term goes through `Query::match_expression`, which quotes tokens that are alphanumeric runs by construction.

Open items:
- Measured while building task 4's ranking case, and worth knowing before phase 6 tunes anything: `entity_score` DWARFS bm25 whenever the query's terms are common. Over a 48-turn store whose every hit carried the queried path, `-bm25` came back at ~1e-6 for every row while the entity weight was 1.2-2.4, so the ranked order was the entity weighting alone with `TAIL`'s tie-breaks deciding the rest. bm25 only becomes load-bearing when a query term is genuinely rare (a free-text-only turn carrying a 3-of-48 term scored 4.65 and took the top three, which is what made the co-occurrence case observable at all). Nothing here is wrong - IDF-weighted entities outranking text is RCL-04 working - but "rank 1..3" is closer to "the three strongest entity matches" than to a text ranking, and the auto-tuner PROJECT.md gates should be told so.
