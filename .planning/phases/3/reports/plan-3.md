Deviations:
- [deviation] The plan orders task 7 last, but task 1's module has no possible consumer before it: the lint gate this contract runs before every commit (`cargo clippy --all-targets -- -D warnings`) reports `Document is never constructed` for a task-1-only commit, and the only files that could consume it at that point are task 7's. Measured, not assumed - those warnings were observed on the task-1-only tree. Landed tasks 1 and 7 as one commit rather than committing a failing lint or an `#[allow(dead_code)]` naming a commit that had not happened yet. Both tasks' Verify criteria are met in full.
- [deviation] Task 2's Verify names `cargo test -p verbatim --test recall_cli` over "each of the three commands", but `search`, `show` and `sessions` are built by tasks 4, 5 and 6, so no such test can exist at task 2 - and `read.rs` has no consumer before task 4, which the same lint gate refuses. Landed tasks 2 and 4 as one commit; the sweep runs over a `READ_COMMANDS` list that tasks 5 and 6 each extended by one line, so the criterion holds over all three from task 6 on.
- [deviation] Task 7's Verify and task 8's both ask that `--json` output keep "every diagnostic on stderr". Observed while writing task 8's sweep: `search`, `show`, `sessions` and `status` emit nothing on stderr in JSON mode because their commentary IS the document, while `verify` and `reindex` printed theirs to both - two accounts of one walk that can disagree. Adopted the uniform rule the plan's own task 7 text implies ("JSON mode puts both in one document on stdout"): with `--json` the document is the answer and stderr carries only warnings. Task 8's property is asserted against a real warning (a store predating this build) rather than against routine commentary, so it is not vacuous. `docs/json-shapes.md` states the rule.
Open items:
- `recall::search::run` resolves the scope before it validates its filters, so a malformed `--since` reaching only the query layer is answered with the scope's reason and exit 0 in a directory no archived project covers. Observed, not assumed - it is what the first version of the misuse test caught. Worked around at the CLI boundary by `cmd::time_bound`, which runs at parse time; the cost is that D-23's two-shape rule now exists twice, in `crates/verbatim/src/cmd/mod.rs` and in the private `recall::search::bound`. Making that helper `pub` and deleting the CLI copy, or reordering `run`'s two steps, is a one-line follow-up for a plan whose lease covers `crates/verbatim-core/src/recall/search.rs`.
- A failure raised before a command reaches its own answer (a store from the future, an unresolvable data directory) writes no `--json` document: the message goes to stderr and the exit code is 1, because the command never got far enough to know `--json` was asked for. Documented in `docs/json-shapes.md` as part of the contract rather than left to be discovered.
- `recall::get::records` puts no server-side cap on how many ids one request may name. `MAX_RESULTS` bounds a search for exactly this reason and the same argument applies here, since each distinct session costs a whole materialized blob. Adding one needs a new `Reason` variant in `crates/verbatim-core/src/recall/scope.rs`, outside this plan's lease. The terminal path is bounded by what a user types; PLAN-4's `recall_get` is where a client-supplied list arrives, so that is where the cap belongs.
- A query that reduces to no tokens (pure punctuation) still returns an empty result with no reason - PLAN-2's open item, inherited unchanged by `verbatim search`, which prints `0 hit(s)` on stderr and nothing else. Not touched: the fix is in `recall::query` / `recall::search`, outside this plan's lease.
