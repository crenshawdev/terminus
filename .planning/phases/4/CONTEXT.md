# Phase 4: Hooks And Install - Context

Gathered: 2026-08-13
Feeds: /cad-plan 4

## Scope boundary

In: The four hook subcommands and their detached ingest spawn, `verbatim install` / `uninstall` / `doctor` across both Claude Code settings files, backfill with an up-front estimate and bounded parallelism, and a thin npm workspace package in this repo proven by `npm pack` plus a local tarball install.
Out: The SessionStart resume brief and any prompt injection, including every `hookSpecificOutput` payload - phase 5 (INJ-01..INJ-06); hooks write nothing to stdout here. Cross-compilation, a tagged release pipeline and any npm registry publish - a later shipping step, not this phase. A Claude Code plugin (`PROJECT.md` bars one in 0.x). Retention, capture mode and `data move` - phase 8.
Deferred: None - the size check kept all nine criteria in this phase.
Plan shape: multiple plans, same phase

## Durable decisions

- D-01 (Hook surface): Hook entries are written in exec form - `{"type":"command","command":"<absolute path>","args":["hook","<event>"]}` - which is the only shape satisfying ING-10's "no shell" on every platform. Evidence: Claude Code 2.1.231 hook schema, `args` described as "Argument list for exec form. When present, `command` is resolved as an executable and spawned directly with these arguments - no shell. When absent, `command` runs through a shell (bash on POSIX, PowerShell on Windows without Git Bash)"; the same bundle carries the "requires bash but Git Bash was not found" error string; `DESIGN-BRIEF.md:119`; `.planning/PROJECT.md:91`. If wrong: a shell-form entry reintroduces the claude-mem Windows failure class the absolute-path choice exists to retire, and a home directory containing a space breaks the command string.
- D-02 (Hook surface): The fourth hook is `PostCompact`, not `PreCompact`. Evidence: compaction is append-only and the `system`/`compact_boundary` record is appended AFTER compaction (`DESIGN-BRIEF.md:132`), so a `PreCompact`-spawned ingest can never see the boundary it exists to record; `DESIGN-BRIEF.md:117` names `PostCompact` and notes neither event can inject. If wrong: every compaction boundary in the corpus is recorded one hook-firing late or not at all, and phase 5's INJ-05 has no `compact_boundary` to derive a dropped-turn set from.
- D-03 (Detached spawn): The spawned child must escape TWO kill mechanisms, not one - a `process.kill(-pid)` on the hook's process group AND a separate breadth-first sweep of the hook's descendant PIDs parsed out of `ps` output. A new process group alone is insufficient if the sweep's snapshot still sees the child parented to the hook. Evidence: Claude Code 2.1.231 `K5_(e,t)` calls `process.kill(-e,t)` and then iterates the descendant list built by `Y5_`, which parses `pid ppid` lines and BFS-walks from the hook pid; `.planning/PROJECT.md:40` names the orphan class this project exists to retire. If wrong: a hook that hits its timeout kills its own ingest mid-pass, AC2 passes against a test that never provokes the real kill, and the failure only appears on long backfills.
- D-04 (Detached spawn): Detachment uses `std` alone - `std::os::unix::process::CommandExt::process_group(0)` and `std::os::windows::process::CommandExt::creation_flags(DETACHED_PROCESS | CREATE_NO_WINDOW)`, all three stdio set to `Stdio::null()`. No `libc`, `nix` or `windows-sys` dependency is added. Evidence: `crates/verbatim-core/src/ingest/lock.rs:12-19` is the precedent - `std::fs::File::try_lock` was chosen because it IS `flock`/`LockFileEx` and pulls in no dependency; every workspace dependency in `Cargo.toml` carries a comment justifying its startup cost; `.planning/PROJECT.md:75`. If wrong: the hook path links a crate it does not need, against a measured 0.408 ms startup floor that is the product.
- D-05 (Install targets): Install writes TWO files - hook entries into `~/.claude/settings.json` under `.hooks`, and the MCP registration into `~/.claude.json` under `.mcpServers`. `settings.json` has no `mcpServers` key. Evidence: measured 2026-08-13, `settings.json` top-level keys are `hooks, cleanupPeriodDays, autoCompactEnabled, env, permissions, ...` with no `mcpServers`; `~/.claude.json` `.mcpServers` holds `context7` and `verbatim`; the 2.1.231 settings schema carries every MCP key EXCEPT `mcpServers`. If wrong: install writes an `mcpServers` block Claude Code ignores, `doctor` reports MCP registered, recall is unreachable from inside Claude Code - and AC4 and AC7 both still pass, because both would only look at settings.json.
- D-06 (Install targets): Install merges `~/.claude.json` itself, reading immediately before an atomic rename-into-place, rather than shelling out to `claude mcp add -s user`. Evidence: `~/.claude.json` is 240 KB carrying 86 `projects` entries plus caches, and Claude Code rewrites it on its own schedule - five rotated backups at 11:07, 11:08, 11:09, 11:11 and 11:12 on 2026-08-13; shelling out would make install depend on `claude` being on PATH, from a binary whose stated contract is no shell and no subprocess. If wrong: install races a running Claude Code and either loses its own write or truncates 240 KB of the user's project history and caches.
- D-07 (Install targets): Install stamps a marker it can recognize on the copy it places at the stable path; an unrecognized binary there is refused with a non-zero exit and the exact command that overwrites it. `doctor` uses the same check. Evidence: measured 2026-08-13, `/home/john/.local/bin/verbatim` is a 12,076,464-byte executable dated Aug 8 whose `--help` reads "capture transcripts before cleanup" with subcommands `precompact, normalize, load, ingest, search, inject, mcp` - a different program - and whose `--version` prints `verbatim 0.1.0`, byte-identical to this build's output (`crates/verbatim/src/main.rs:64` prints `CARGO_PKG_VERSION`, workspace version `0.1.0`); `~/.claude.json` already registers an MCP server named `verbatim` pointing at that file. If wrong: install silently overwrites a file it did not create, version alone cannot tell the two apart, and uninstall then either deletes the incumbent or refuses to clean up.
- D-08 (Install targets): The canonical stable path is `~/.local/bin/verbatim` on Linux and macOS and `%LOCALAPPDATA%\Programs\Verbatim\verbatim.exe` on Windows, and install never modifies PATH. Evidence: `DESIGN-BRIEF.md:400`; INST-02. If wrong: hook entries point at a path that moves between installs, which is the version-skew class `PROJECT.md:103` designs out by writing hooks once and never rewriting them.
- D-09 (Install targets): Install sources the platform binary from `std::env::current_exe()` - the npm shim execs the per-platform binary, so the running process IS the copy source and install needs no knowledge of npm layout. Evidence: `DESIGN-BRIEF.md:426` ("copies the platform binary out of the npm package to the stable path ... the npm shim execs it, so there's one binary and no version skew"); `.planning/PROJECT.md:103` bars a postinstall script, which removes the only other moment npm could place the file. If wrong: install has to reimplement npm's platform-package resolution in Rust, and gets it wrong on exactly the platforms it cannot test.
- D-10 (npm package): The thin package's `bin` entry is a JS shim that resolves the platform package and execs the binary; the `bin` field cannot point into an optionalDependency. Evidence: npm's `bin` field only references paths inside the declaring package, which is why esbuild-style packaging ships a shim; `DESIGN-BRIEF.md:418` names the esbuild pattern and "No postinstall script"; `.planning/PROJECT.md:78`. If wrong: `npx verbatim install` resolves to nothing on every platform, or works only where npm happens to hoist the optional package into a reachable location.
- D-11 (Backfill): Bounded parallelism is a fixed count of `std::thread` workers doing parse and zstd compression with a single thread owning the SQLite writes, spawned only inside the backfill command. No `rayon`, no global pool. Evidence: `crates/verbatim-core/src/lib.rs:1-7` states the crate "links no async runtime, no HTTP client and no thread pool"; `Cargo.toml` has no rayon; `.planning/PROJECT.md:39` bars an async runtime because "cold start is the metric - the hook path must not pay for a runtime it doesn't use"; measured startup floor 0.408 ms over 50 `--version` runs. If wrong: the crate that serves the hook path links a thread pool for a command the hook path never runs, and `lib.rs`'s own claim becomes false.
- D-12 (Doctor): `verbatim doctor` opens the store through the read-only path (`crates/verbatim/src/cmd/read.rs`, phase 3 D-10), never `Store::open`. Evidence: `crates/verbatim/src/cmd/status.rs:40` is `Store::open(&data_dir)?` and `crates/verbatim-core/src/store/open.rs:101-119` shows `Store::open` doing `create_dir_all`, `initialize()`, `bring_forward` and `pragma_update(journal_mode=wal)`; `read.rs`'s test `an_empty_data_directory_is_a_reason_and_creates_nothing` already asserts the opposite behaviour; INST-06 requires doctor be read-only and never repair. If wrong: doctor on a machine that never ingested creates the data directory and an empty WAL database, so its own "store openable" check passes because the check created the store.
- D-13 (Uninstall): Uninstall removes exactly the entries whose `command` equals the stable path plus the `verbatim` key under `.mcpServers`, and restores the whole-file backup only when the file is byte-identical to that backup. Evidence: INST-07 ("removes only what install added, restores the settings backup when the file is otherwise unchanged"); `~/.claude/settings.json` carries 29 top-level keys including `theme`, `model`, `effortLevel`, `voice` and `statusLine`, all written by Claude Code's own UI between install and uninstall. If wrong: uninstall reverts a `/config` change the user made after installing, or refuses to clean up at all because an unrelated key moved.

## Decisions

- D-14 (Hook surface): The hook subcommand reads exactly one line of JSON on stdin followed by EOF, and may rely on the base fields `{session_id, transcript_path, cwd, permission_mode}` plus per-event extras - `SessionStart{source, agent_type, model, session_title}`, `UserPromptSubmit{prompt, session_title}`, `SessionEnd{reason}`, `PostCompact{trigger, compact_summary}`. Evidence: Claude Code 2.1.231 builds the base payload in `hg(e,t,r,n)` and spreads it per event, then `stdin.write(n+"\n"); stdin.end()`; `crates/verbatim/src/cmd/mcp/mod.rs:101` is the only existing stdin reader in the repo.
- D-15 (Hook surface): The hook subcommands write nothing to stdout in this phase - no JSON, no `hookSpecificOutput`. Evidence: roadmap AC1 asks for clean stdout; `DESIGN-BRIEF.md:113-117` gives `SessionEnd` and the compact hook no synchronous work and defers the brief and the entity query to INJ-01/INJ-03; the 2.1.231 bundle validates any stdout that parses as JSON against the event name.
- D-16 (Hook surface): The supported Claude Code floor for exec-form hooks is pinned at 2.1.227, and `doctor` reports a below-floor Claude Code as a problem. Evidence: `args` measured present in 2.1.227, 2.1.229 and 2.1.231 on this machine; the release that introduced it is not established, so the floor is the oldest version measured rather than the true minimum.
- D-17 (Hook surface): Hook entries written into settings.json are picked up by a running Claude Code without a restart, so install prints that hooks are live - and must therefore tolerate writing settings.json while Claude Code is itself writing it.
- D-18 (Detached spawn): All four hooks spawn the same `verbatim ingest` tree pass with no per-file argument; the ingest lock collapses concurrent spawns and nothing new is needed for exclusivity or resumability. Evidence: `crates/verbatim-core/src/ingest/pass.rs:87-97` takes the lock before opening the store and returns `PassOutcome::LockHeld`; `crates/verbatim/src/cmd/ingest.rs:41-43` maps that to exit 0 with empty stdout; `crates/verbatim-core/src/ingest/lock.rs:56-59` states the hook spawn is the scheduler and a second invocation is normal; `crates/verbatim/tests/lock_race.rs` already exercises it; a steady-state pass over 2,244 files measured 92 ms on 2026-08-13.
- D-19 (Install targets): `~/.claude.json` is treated as the durable home for `.mcpServers`, to be re-checked at 1.0. Evidence: measured there on 2026-08-13; the 2.1.231 bundle carries strings about migrating OTHER state out of that file (`migrateEnableAllProjectMcpServersToSettings`, legacy approvals), not `mcpServers` itself.
- D-20 (Install targets): Confirmation, `--yes` and non-TTY behaviour are entirely new code - there is no prompting, no `IsTerminal` and no interactive path anywhere in the repo. Evidence: `grep -rn "stdin()"` across `crates/*/src/` returns exactly one hit (`cmd/mcp/mod.rs:101`); `IsTerminal|is_terminal|atty` returns nothing; `crates/verbatim/src/cmd/mod.rs:12-34` documents a contract in which every command is non-interactive.
- D-21 (npm package): The npm package lives as a workspace directory in THIS repo and is proven by `npm pack` plus installing the resulting tarball locally; cross-compilation, release CI and registry publish are out of this phase. Evidence: user-settled scope fork; the repo has no `package.json` and no JS outside `target/`; `node` v26.7.0 and `npm` 12.0.2 are present on this machine; the release binary is 4,969,688 bytes, 2.15 MB gzipped.
- D-22 (Backfill): Backfill is `pass::run` with an estimate printed in front of it and a detached spawn around it; resumability needs no new state, coming from the per-file watermarks and per-file transactions phase 2 already ships (phase 2 D-11). Evidence: `crates/verbatim-core/src/ingest/pass.rs:1-27`; `crates/verbatim-core/src/ingest/mod.rs:380` `write_watermark`; `crates/verbatim/tests/crash.rs` resumes to a byte-identical reference store across 24 SIGKILLs; `crates/verbatim-core/src/discover.rs:24-26` states outright that bounded-parallelism backfill is phase 4's.
- D-23 (Backfill): The estimate is calibrated against a measured single-threaded rate rather than a guess - the full real corpus (2,248 `.jsonl` files, 1.1 GB at `/data/claude/.claude/projects`) ingested in 36,582 ms on 2026-08-13, producing a 735 MB store of 2,244 sessions and 274,422 turns, with the following steady-state pass at 92 ms.
- D-24 (CLI contract): `doctor` accepts `--json` and emits named checks; `install` and `uninstall` stay human-only, because an interactive confirmation and a stdout JSON document contradict each other. Evidence: `crates/verbatim/src/cmd/mod.rs:12-34` scopes the `{command, ok, reason, data}` envelope to "every data command"; `docs/json-shapes.md` calls itself the CLI data contract; no INST requirement mentions `--json`.

## Acceptance criteria

- [ ] AC1: Feeding each of the four hooks (SessionStart, UserPromptSubmit, SessionEnd, PostCompact) the exact JSON Claude Code sends on stdin returns exit 0 with empty stdout, at p99 under 10 ms wall over 100 runs.
- [ ] AC2: A hook killed the way Claude Code kills one - SIGKILL to the process group, then SIGKILL to every descendant PID a `ps` walk finds - leaves the spawned ingest alive and its pass completing to a committed store.
- [ ] AC3: On Windows the spawned child shows no console window and holds no handle inherited from the hook. (human-verify: needs a Windows machine)
- [ ] AC4: Running `verbatim install` twice leaves exactly one hook entry per hook in settings.json and exactly one `verbatim` entry in `~/.claude.json` `.mcpServers`, with one backup of each file written on the first run only, and every other key in both files byte-identical to before.
- [ ] AC5: Replacing the binary and rerunning install changes no byte of settings.json's `hooks` object; install against a stable path holding a binary without verbatim's marker exits non-zero, writes nothing to either file, and prints a command that makes the same install succeed.
- [ ] AC6: `verbatim doctor` against a data directory that does not exist creates no file or directory, and against a hook path pointing at a missing binary reports the problem and prints a command that, when run, makes the same check pass.
- [ ] AC7: Uninstall on a settings.json unchanged since install restores it to its pre-install bytes, removes only the `verbatim` key from `.mcpServers`, and leaves the data directory present, printing its path.
- [ ] AC8: Backfill over the real corpus prints a session count, byte total and time estimate before any ingest work and returns the shell in under 100 ms; killed mid-pass and rerun, it converges to the same store contents as an uninterrupted run.
- [ ] AC9: `npm pack` on the in-repo workspace and installing the resulting tarball puts a working `verbatim` on the path whose `--version` matches the Rust build, with no postinstall script in the package.

## Flagged assumptions

- The 2.1.227 floor in D-16 is the oldest version measured to carry exec-form `args`, not the release that introduced it - Likely; if wrong: doctor reports a false problem on a Claude Code that is actually fine, and the documented minimum is stricter than it needs to be.
- D-17's mid-session hot-reload holds for the Claude Code versions on this machine and is not a documented contract - Likely; if wrong: install prints "hooks are live" when they will not fire until the next session, and the user concludes the install failed.
- `crates/verbatim/src/cmd/json.rs` `Document::emit` uses `println!`, which panics with exit 101 on a closed stdout pipe while the human path has broken-pipe handling (`.planning/CAPTURE.md`, phase 3) - Confident; if wrong for `doctor --json` (D-24): `verbatim doctor --json | head` exits 101 and doctor reports a failure that is its own.
- Whether `npm pack` plus a local tarball install exercises the same resolution path a registry install would, given the platform package is resolved from the local workspace rather than the registry - Unclear; if wrong: AC9 passes locally and `npx verbatim install` still fails for a stranger, and the gap only shows at the publish step in a later phase.
