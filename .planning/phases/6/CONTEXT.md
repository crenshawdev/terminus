# Phase 6: Signed Install - Context

Gathered: 2026-10-14
Feeds: /cad-plan 6

## Scope boundary

In: `install.sh` pins the release key's public line under the principal `crenshawdev-release`, downloads `terminus-<os>-<arch>.manifest.sig` from the same source as the manifest, and runs `ssh-keygen -Y verify` with the namespace `terminus-release` before the manifest is parsed. A machine without `ssh-keygen` is refused before any download. The SHA-256 check in `verify_download`, the version folders, the link and the final `terminus install` stay as Phases 4 and 5 built them. The install.sh tests sign with a throwaway key through a key-swapped copy of the script and run under `/bin/sh` and dash. `CHANGELOG.md` Unreleased, `DESIGN-BRIEF.md` §13 and the `install.sh` header comment are brought in line, and `PROJECT.md` lines 21 and 23 are corrected with text the owner approves at plan review.
Out: release CI, the signing script and publishing a release (phase 7), the README (phase 8), changing Baley's `install.sh`, changing the workspace version from 0.1.1, a version check on `ssh-keygen`, and qualifying on macOS.
Deferred: None.
Plan shape: multiple plans, same phase. Suggested order: the script with its tests, then the docs and `PROJECT.md`, so the `PROJECT.md` text is reviewed in a plan of its own.

## Durable decisions

- D-01 (Where the check sits): The signature check is its own step, after the downloads and before the manifest is parsed at `install.sh:189-211`. `verify_download` stays the SHA-256 check on the binary. This replaces the plan in the `install.sh` header, the CHANGELOG and phase 4 D-06, which all put the check inside `verify_download`: there it would run after an unverified manifest had already been read, and criterion 2 would fail. Baley's ADR 0038 and its `install.sh:3` still name `verify_download` as the place, so Baley #14 gets a different shape unless it copies this one. Evidence: `.planning/ROADMAP.md` (phase 6 goal), `install.sh:5-6,84-88,184-213`, `CHANGELOG.md:30-31`, `.planning/phases/4/CONTEXT.md` (D-06), `/code/baley/docs/adr/0038-installer-and-opt-in-updates.md`, `/code/baley/install.sh:3`.
- D-02 (Signing in tests): The tests that expect a successful install run a copy of `install.sh` with the pinned public line swapped for a throwaway Ed25519 key made per fixture. The unmodified `install.sh` runs for the "made by another key" refusal. The private half of the pinned key exists only on the owner's machine, so no test can sign with it. A fake `ssh-keygen` that exits 0 was rejected because real verification would never run, and a committed throwaway private key was rejected because secret scanners flag OpenSSH private keys. Evidence: `crates/terminus/tests/install_script.rs:121-136` (a throwaway TLS certificate per test, the precedent), `:284-286` (`script()` runs the real file), `:749-756` (the cut-off test needs the file to end in `\n}\n`); `~/.ssh/crenshawdev-release.pub` matches the pinned line exactly (checked 2026-10-14).

## Decisions

- D-03 (Download order): The downloads run in this order: manifest, signature, verify, then binary. A refused release never downloads the binary. `default_urls()` and both no-argument tests change to the three-URL order. Evidence: `install.sh:184-187`, `crates/terminus/tests/install_script.rs:705-723`.
- D-04 (No escape hatch): Every source must carry a signature by the pinned key, including one passed as the `https://` argument, so a custom source can only serve releases the owner signed, such as a mirror. There is no unsigned or development mode. A local build still installs with `cargo build --release && target/release/terminus install`. Evidence: `.planning/REQUIREMENTS.md:27` (INST-14, "nothing overrides it"), `.planning/ROADMAP.md` (phase 6 criterion 5), `install.sh:121-130`, `.planning/phases/4/CONTEXT.md` (D-02).
- D-05 (Missing `ssh-keygen`): The check for `ssh-keygen` runs before any download, next to the `uname` refusals, with `command -v` as `digest` uses it. The message names all three package names: `openssh-client` (Debian, Ubuntu), `openssh-clients` (Fedora) and `openssh` (Arch). On this machine `ssh-keygen` belongs to `openssh 10.6p1-1.1` (`pacman -Qo`, 2026-10-14). The owner chose all three over `openssh-client` alone. Evidence: `install.sh:75-82,162-171`, `.planning/ROADMAP.md` (phase 6 criterion 3).
- D-06 (Principal and allowed signers): The principal is `crenshawdev-release`, matching the key's file name and the GitHub org, and Baley uses the same name for the same key. The script writes the allowed-signers line `crenshawdev-release <pinned public line>` from its own literal into the existing `mktemp -d` scratch folder, and runs `ssh-keygen -Y verify -f <that file> -I crenshawdev-release -n terminus-release -s <manifest.sig>` with the manifest on stdin. Nothing is read from HOME, `~/.ssh` or any file the user controls. The principal is not inside the signature, so phase 7's signing never names it. Measured 2026-10-14 with OpenSSH 10.6p1 under `env -i ... dash`, two throwaway keys and eleven verify cases: `-Y verify` reads the message only from stdin, so `-f /dev/stdin` cannot also carry the allowed-signers line; a `baley-release` signature was refused with or without a `namespaces=` option on the line; another key's signature, a tampered manifest, an empty file, a non-SSHSIG text file and a missing file were all refused with exit 255. Evidence: `install.sh:173-181`, owner's ruling at context.
- D-07 (Output): The script prints its own refusal reason on stderr through `fail` and does not show `ssh-keygen`'s output. Measured in the same eleven cases: every refusal prints "Could not verify signature." on stdout, a success prints `Good "terminus-release" signature for ...` on stdout, and a wrong-key or wrong-principal refusal leaves stderr empty. Passed through, that output would put refusals on stdout and the "Good" line inside the install receipt. Evidence: `install.sh:19-22`, `crates/terminus/tests/install_script.rs:573-582`.
- D-08 (Two messages): A missing signature is a download failure, `signature download failed: <url>`, in the form the manifest and binary lines use. A bad signature is a refusal saying the manifest does not verify against the pinned key. One message for both would hide a release whose `.sig` was never uploaded behind what looks like tampering. Evidence: `install.sh:184-187`, `crates/terminus/tests/install_script.rs:805-832`.
- D-09 (No version check): The script does not check `ssh-keygen`'s version. Any non-zero exit from `-Y verify` is a refusal. An `ssh-keygen` too old for `-Y` fails closed. Evidence: `install.sh:75-82`; all verify failures exited 255 on OpenSSH 10.6p1 (measured 2026-10-14).
- D-10 (Criterion 5 in tests): Two tests show it: the real `install.sh` refuses a release signed by a throwaway key, and a source test like `install_sh_holds_the_same_marker` checks that the pinned line appears in `install.sh` exactly once, as a literal. The source test also keeps D-02's swap honest, because a swap that finds nothing to replace would run the success tests against the wrong key. Evidence: `crates/terminus/src/cmd/install/binary.rs:412`, `.planning/ROADMAP.md` (phase 6 criterion 5).
- D-11 (Missing-signature test): The missing-signature refusal runs on the fake `curl` exiting 22, because `s_server -WWW` answers a missing file with `200 ok` and error text, which would test a bad signature instead. The refusal leaves the stable path and the versions folder unchanged, as `assert_refused` checks. A non-SSHSIG text file as the signature fails with "Couldn't parse signature: missing header", exit 255 (measured 2026-10-14). Evidence: `crates/terminus/tests/install_script.rs:25-27,521-543,560-582`.
- D-12 (`ssh-keygen` in tests): `ssh-keygen` joins `TOOLS`, and the tests require it on `PATH` and skip nothing, as they do for dash. Left out, the test `PATH` holds only links, so every run hits the `ssh-keygen` refusal. Baley's rule against running `ssh-keygen` in tests (`/code/baley/AGENTS.md:63`) does not apply to Terminus, which has no `AGENTS.md`. Evidence: `crates/terminus/tests/install_script.rs:7,36-50,194-200,342-356`.
- D-13 (Re-signing): Each `serve` signs the manifest again and replaces the earlier signature, because many tests serve twice, for example 1.0.0 then 2.0.0. Signing goes from stdin to stdout: `ssh-keygen -Y sign -f k -n terminus-release <file>` stops at "Overwrite (y/n)?" when `<file>.sig` exists, and the measurement hung until its 120 s timeout. Evidence: `crates/terminus/tests/install_script.rs:389-402,805-816,861-869`.
- D-14 (Docs): The `CHANGELOG.md` Unreleased section, `DESIGN-BRIEF.md` §13 and the `install.sh` header comment describe the signature check, the pinned key and the need for `ssh-keygen`. The "unsigned development artifacts only" and "inside verify_download" lines go. "No release is published yet" stays until phase 7. Evidence: `CHANGELOG.md:30-31`, `DESIGN-BRIEF.md:381,395`, `install.sh:2-6`, `.planning/phases/5/UAT.md`.
- D-15 (`PROJECT.md`): Lines 21 and 23 are corrected in this phase. Line 23 says "No release is published until the update feature is built", and line 21 says "Six phases" and that updates come in a later cycle with the signing Baley's #14 owns. Both contradict the owner's 2026-10-14 ruling: the first release, 0.1.0, ships with signing, does not wait for Baley, and updates by rerunning `install.sh`. The plan carries the exact replacement text, and the owner approves it at plan review before it is written. The owner chose this phase over phase 7 and over leaving it. Evidence: `.planning/PROJECT.md:21,23`.

## Acceptance criteria

- [ ] AC1: `install.sh` contains the line `ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIDRKdhQ8g59SckbR4oYy0JQlObLTSwfVjGa9UqwoPo4q` exactly once. A run with no argument requests the default source's `terminus-<os>-<arch>.manifest`, `terminus-<os>-<arch>.manifest.sig` and `terminus-<os>-<arch>`, in that order.
- [ ] AC2: The run exits non-zero with a reason on stderr in each of these cases: the signature is missing, it was made by another key, it was made under the namespace `baley-release`, or the manifest was changed after signing. In every case the binary is never requested, and the stable path and the versions folder are unchanged. A missing signature reports `signature download failed: <url>`.
- [ ] AC3: With no `ssh-keygen` on `PATH`, the run exits non-zero before any download. The message names `openssh-client`, `openssh-clients` and `openssh`, and nothing under HOME changes.
- [ ] AC4: A correctly signed release installs as it did in Phase 5, under both `/bin/sh` and dash, and no `ssh-keygen` output appears in what the run prints. `sh -n install.sh` and `dash -n install.sh` pass, and `cargo test --workspace --all-features` passes.
- [ ] AC5: The unmodified `install.sh` refuses a release signed by a throwaway key, even when that key is listed in `$HOME/.ssh/allowed_signers`.
- [ ] AC6: The `CHANGELOG.md` Unreleased section, `DESIGN-BRIEF.md` §13 and the `install.sh` header describe the signature check, the pinned key and the need for `ssh-keygen`. None of them still says "inside verify_download" or "unsigned development artifacts only", and they still say no release is published yet. `PROJECT.md` no longer says a release waits for the update feature, or that updates come with Baley's #14 signing.

## Flagged assumptions

- The oldest OpenSSH whose `ssh-keygen` has `-Y verify` with `-I`, `-n` and an allowed-signers file is unmeasured. The recollection at context, unchecked, is 8.1 (2019), which would cover Ubuntu 20.04 and Debian 11. - Unclear; if wrong: on an older OpenSSH a correctly signed release is refused as a bad signature. It is never installed unverified.
- What an `ssh-keygen` too old for `-Y` prints and exits with is unknown, so the script cannot tell "cannot verify" from "bad signature" (D-09). - Unclear; if wrong: the refusal on such a machine reads as a bad signature rather than an old OpenSSH.
- macOS's bundled `ssh-keygen` handles `-Y verify` and the allowed-signers file the same way OpenSSH 10.6p1 does. Phase 7's last criterion installs on real macOS runners and is where this is proven. - Unclear; if wrong: the one-line install refuses every release on a Mac.
- Whether the allowed-signers line also carries `namespaces="terminus-release"` is the planner's call. `-n` alone refused a `baley-release` signature in the measurement. - Confident; if wrong: nothing changes for this phase.
- macOS stays unqualified, as phases 4 and 5 left it: BSD `grep`, `mktemp`, `readlink` and `mv -f`, `current_exe()` through a link, and an unsigned binary on aarch64. - Unclear; if wrong: the one-line install fails on a Mac, which phase 7 is the first to run.
