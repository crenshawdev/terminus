## Scope boundary

In: The Linux binaries become static musl builds with mimalloc as the global allocator, and the macOS binaries link only the system libraries every Mac has. The workspace version goes from 0.1.1 to 0.1.0 in `Cargo.toml` and `Cargo.lock`, and `git.create_tag` is turned off in the repo config. A release workflow fires on `v<X.Y.Z>` tags, builds the four platforms natively, writes each manifest and makes one draft release. A signing script in this repo rechecks the four binaries, signs the four manifests with the owner's key, verifies each signature as `install.sh` does, uploads the `.sig` files and publishes. Phases 1 to 8 land on `main`, `v0.1.0` is tagged on `main`, and the release is published. A check workflow then installs the release on all four runners with the one-line command. After publishing, the "no release is published yet" lines, the CHANGELOG's Unreleased section and PROJECT.md's remote line are corrected. Any macOS failure the build or the check finds is fixed here.
Out: The README (phase 9). Running the test suite in CI. Changing Baley's `install.sh` or its release design (Baley #14). An update feature beyond rerunning `install.sh`. Windows.
Deferred: None.
Plan shape: multiple plans, same phase. Suggested order: the musl build with mimalloc and its hook timing, then the two workflows, then the signing script with its tests, then the live release (land on `main`, tag, sign, publish, check) and the doc corrections after it. The live release goes last because it needs `main` landed and the owner's key, and a published release cannot be taken back. ## Durable decisions

- D-01 (Linking): The Linux binaries target `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`, are statically linked, and use mimalloc as the global allocator on musl targets. The macOS binaries link only the system libraries under `/usr/lib/`; Apple does not support fully static binaries. The owner's rule: nothing may need installing for Terminus to run on a supported OS, and the best option is used. mimalloc was chosen because musl's own allocator is much slower than glibc's under multi-threaded allocation, and backfill allocates across rayon threads. It is compiled into the binary, so it adds no runtime dependency. That choice is a judgment, not a measurement on Terminus, and AC6 measures it. A glibc build was rejected: built on Ubuntu 24.04 it needs glibc 2.39 and does not start on Ubuntu 22.04 or Debian 12, which breaks the brief's static-binary rule. musl with its own allocator was rejected on the slowdown. Evidence: `DESIGN-BRIEF.md:37`, `.planning/PROJECT.md:100`; `target/release/terminus` is dynamically linked to `libc.so.6`, `libm.so.6` and `libgcc_s.so.1` and needs `GLIBC_2.39` (`ldd`, `objdump -T`, 2026-10-14); `Cargo.toml` (rusqlite `bundled`, zstd); `crates/terminus/tests/corpus.rs:400-430` (the 10 ms release wall).
- D-02 (Release from `main`): A release is cut from `main` after landing. For 0.1.0, phases 1 to 8 land on `main` first, `v0.1.0` is tagged on `main`, the release is published, and phase 9's README follows on top. The check after publishing runs the public one-line command, which fetches `install.sh` from `main`, and today `origin/main` has no `install.sh` and `cadence/v0.0.1` is not on `origin`. A tag cut on the integration branch can end up off `main` after a non-fast-forward merge. Having the check fetch `install.sh` at the tag was rejected because it would not test the public command. Evidence: `git ls-tree origin/main install.sh` is empty and `git ls-remote --heads origin` lists only `main`, `phase-2-ingest-at-scale` and `terminus-rename` (2026-10-14); `.planning/phases/5/CONTEXT.md` (D-07); `cad-land/SKILL.md:255-266`. [changed 2026-10-14 by the owner: the README (phase 9) lands before the release, and the live release (land, tag, sign, publish, check) moved to phase 10]
- D-03 (Tag name): Version tags are `v<X.Y.Z>`, starting with `v0.1.0`, and the release workflow fires on that pattern only. It matches Baley's `v3.7.12` tag and the `v0.1.0` and `v0.1.1` annotations on the renamed Verbatim tags. `git.create_tag` is turned off in this repo's `.planning/config.json`, because `/cad-land` would otherwise cut a bare `0.1.0` tag that builds nothing. A bare `X.Y.Z` tag was rejected because it differs from Baley. Evidence: `git -C /code/baley tag --list`, `git for-each-ref refs/tags`, `cad-land/SKILL.md:255-263`, `.planning/config.json` (`git.create_tag: true`).
- D-04 (Version): The workspace version goes from 0.1.1 to 0.1.0, together with Cargo.lock's two terminus entries, so the first release is 0.1.0 as `CHANGELOG.md` and PROJECT.md say. Installing the release moves the owner's link from the local 0.1.1 build back to 0.1.0, and nothing refuses a lower version. Releasing 0.1.1 and correcting the docs was rejected. Evidence: `CHANGELOG.md:6-7`, `.planning/PROJECT.md:23`, `Cargo.toml:6`, `Cargo.lock:424,435`; `~/.local/bin/terminus --version` prints `0.1.1` (2026-10-14).

## Decisions

- D-05 (Release files): Each release carries the names phase 5 D-01 fixed: `terminus-<os>-<arch>`, `terminus-<os>-<arch>.manifest` and `terminus-<os>-<arch>.manifest.sig`, with `<os>` `linux` or `macos` and `<arch>` `x86_64` or `aarch64`. Each manifest is exactly `version X.Y.Z\n` then `sha256 <64 lowercase hex>\n`, holding only the hash and not the file name `sha256sum` prints after it. Evidence: `install.sh:190-226`, `CHANGELOG.md:20-28`, `.planning/phases/5/CONTEXT.md` (D-01).
- D-06 (Native builds): Each platform is built on its own runner (Linux x86_64, Linux aarch64, Intel macOS, arm64 macOS) with no cross-compiling, and the same four runners run the check. A cross-built binary is never run where it was built, so a broken one would first show up after signing. This depends on the Intel macOS runner, which the planner checks first. Evidence: `Cargo.lock` (`cc`, `zstd-sys`, `libsqlite3-sys`), `install.sh:171-175`, `.planning/ROADMAP.md` (phase 8 criterion 4).
- D-07 (Version check): The manifest's `version` comes from the built binary's `terminus --version`, which prints the bare `CARGO_PKG_VERSION`. The workflow makes no draft when that differs from the tag's version. Evidence: `crates/terminus/src/main.rs:95-97`, `crates/terminus/src/cmd/install/binary.rs:204,214-217`, `.planning/ROADMAP.md` (phase 8 criterion 1).
- D-08 (Build command): The release build is `cargo build --release --locked` of the `terminus` package with no features turned on and the existing `[profile.release]`, so `testkit`'s fault-injection points never ship. Evidence: `crates/terminus/Cargo.toml` (`testkit`), `Cargo.toml` (`[profile.release]`), `/code/baley/.github/workflows/test.yml`.
- D-09 (Workflow style): The workflows follow Baley's `test.yml`. The top level sets `permissions: contents: read`, only the job that makes the draft raises it to `contents: write`, actions are pinned by full commit SHA, and the Rust version is named rather than taken from the runner image. Terminus has no `.github/` today and never had one. Evidence: `/code/baley/.github/workflows/test.yml`, `/code/baley/rust-toolchain.toml`; `git log --all -- .github` is empty; the repo's `default_workflow_permissions` is `read` (`gh api`, 2026-10-14).
- D-10 (Draft): The draft is made only after all four builds pass, by one job that attaches all eight files. A failed platform leaves no draft. Evidence: `.planning/ROADMAP.md` (phase 8 criterion 1); `gh release list --repo crenshawdev/terminus` is empty (2026-10-14).
- D-11 (No secrets): No workflow uses the `secrets.` context. The draft is made with the job's `github.token`. A test reads `.github/workflows/*` and fails on `secrets.`, `-Y sign` or a private-key header, the way the existing tests tie `install.sh` to the marker and the key. Evidence: `crates/terminus/src/cmd/install/binary.rs:409-420`, `crates/terminus/tests/install_script.rs:1237-1250`; the repo has 0 Actions secrets and 0 environments (`gh api`, 2026-10-14).
- D-12 (Signing script): The signing script lives in this repo and is POSIX sh like `install.sh`. It uses `gh` for the release. It signs each manifest from stdin to stdout with `ssh-keygen -Y sign -f ~/.ssh/crenshawdev-release -n terminus-release`, which avoids the "Overwrite (y/n)?" stop. It reads the pinned key from `install.sh`'s `release_key=` line and keeps no copy of its own. Evidence: `.planning/phases/6/CONTEXT.md` (D-13), `crates/terminus/tests/install_script.rs:447-467`, `install.sh:21`; `gh` 2.102.0 is logged in as crenshawdev and `~/.ssh/crenshawdev-release.pub` matches the pinned line (2026-10-14).
- D-13 (Passphrase): The script signs with the key file and accepts one passphrase prompt per manifest, four per release. It does not assume an agent holds the key. A short-lived `ssh-agent` that takes the passphrase once was the alternative and was not chosen. Evidence: `~/.ssh/crenshawdev-release` is 464 bytes, the size of an encrypted Ed25519 key with that comment (contents not read); `ssh-add -l` found no agent (2026-10-14).
- D-14 (Verify before publishing): Before uploading anything, the script checks each signature with exactly the command `install.sh` runs: the allowed-signers line `crenshawdev-release <key>` in a `mktemp -d` folder, `-I crenshawdev-release -n terminus-release`, and the manifest on stdin. It uploads the four `.sig` files and publishes only after all four pass. Evidence: `install.sh:196-199`, `DESIGN-BRIEF.md:407`, `.planning/ROADMAP.md` (phase 8 criterion 2).
- D-15 (Recheck): Before signing, the script downloads the four binaries and checks each against its manifest's SHA-256. This catches a draft whose binary does not match its manifest before any user sees it. It does not guard against CI building something bad, since CI wrote both files. Evidence: `install.sh:88-92,228`, `.planning/ROADMAP.md` (phase 8 goal).
- D-16 (Latest, not prerelease): The release is published as a normal release marked latest, not as a prerelease, because `releases/latest/download` skips prereleases and the one-line command would fail. Evidence: `install.sh:127`, `CHANGELOG.md:6-7`.
- D-17 (Check trigger): The check workflow fires on `release: published` and runs on the same four runners as the build. It fires because the owner's own `gh` login publishes the release; a release published with a workflow's `GITHUB_TOKEN` would start no other workflow. Evidence: `.planning/ROADMAP.md` (phase 8 criterion 4), `gh auth status`.
- D-18 (Stand-in `claude`): The check puts a stand-in `claude` on `PATH`, as the tests do, so the one-line command exits 0. It then runs `~/.local/bin/terminus --version` by full path and requires the release version. Without it, `terminus install` exits non-zero because it cannot register the MCP server. Installing the real Claude Code was rejected because it makes the check depend on Claude Code's installer on every runner. Evidence: `crates/terminus/src/cmd/install/mod.rs:228-240`, `install.sh:12,269`, `crates/terminus/tests/install_script.rs:19-21,298`, `crates/terminus/src/cmd/install/binary.rs:5-8`.
- D-19 (macOS fixes): A macOS failure found by the build or the check is fixed in this phase, because criterion 4 cannot pass otherwise. The macOS code paths have never been compiled. Evidence: `crates/terminus-core/src/config.rs:928`, `crates/terminus-core/src/store/open.rs:909`; only `x86_64-unknown-linux-gnu` is installed locally (`rustup target list --installed`, 2026-10-14); `.planning/phases/6/CONTEXT.md` (flagged assumptions).
- D-20 (No suite in CI): The release workflow only builds. It does not run the test suite, which has never run on macOS. Running the tests on the two Linux runners before the draft was the alternative. Evidence: `.planning/ROADMAP.md` (phase 8 criteria), `crates/terminus/tests/install_script.rs` (needs `dash` and `ssh-keygen`).
- D-21 (Docs after publishing): The "no release is published yet" lines change only after the release is published, and the CHANGELOG's Unreleased section becomes the 0.1.0 section. PROJECT.md's "`origin` (self-hosted) is the only remote" is corrected with them: `origin` is github.com/crenshawdev/terminus and `forgejo` is the self-hosted verbatim.git. Evidence: `install.sh:2`, `DESIGN-BRIEF.md:382,501`, `CHANGELOG.md:43-44`, `.planning/PROJECT.md:106`, `.planning/phases/6/CONTEXT.md` (D-14); `git remote -v` (2026-10-14).

## Flagged assumptions

- GitHub still offers an Intel macOS runner (`macos-13` is retired) and a free arm64 Linux runner (`ubuntu-24.04-arm`) for public repos. The planner checks this first. - Unclear; if wrong: the x86_64 macOS binary is built on an arm64 Mac, D-06 does not hold, and criterion 4 cannot run that binary on its own runner.
- macOS's bundled `ssh-keygen` runs `-Y verify -f <allowed_signers> -I -n` as OpenSSH 10.6p1 does, and the Ubuntu runner's OpenSSH is new enough for it. Carried from phase 6. - Unclear; if wrong: the one-line install refuses every release on that runner, and D-19 makes it this phase's fix.
- `gh release download`, `upload` and `edit --draft=false` can find a draft by its tag name, though the REST `releases/tags/{tag}` lookup does not return drafts. - Unclear; if wrong: the signing script finds the draft by its release id instead.
- A release published with the owner's `gh` login fires `release: published`, and `releases/latest/download` picks the newest normal 0.x release. - Likely; if wrong: the check never starts on its own, and the signing script starts it with `workflow_dispatch` instead.
- An arm64 macOS binary keeps the linker's ad-hoc signature through the release profile's `strip = "debuginfo"`, and a binary fetched with curl carries no quarantine flag, so it runs unsigned. - Unclear; if wrong: the arm64 Mac refuses to run the binary, and D-19 makes it this phase's fix.
- zstd-sys and libsqlite3-sys (`bundled`) build for musl on the arm64 Ubuntu runner, and mimalloc builds for both musl targets. - Unclear; if wrong: the Linux builds need a different musl C toolchain.
- A GitHub Actions `run:` step fails when curl fails inside `curl ... | sh`, which depends on whether the default shell sets `pipefail`. - Unclear; if wrong: a 404 on `install.sh` passes the install step, and only the `--version` step shows the failure, so the check sets the shell explicitly.
- mimalloc keeps the hook inside its 10 ms budget and speeds up backfill over musl's allocator. Neither is measured on Terminus. - Likely; if wrong: AC6 fails and the allocator choice in D-01 is revisited.
